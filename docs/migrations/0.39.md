# 0.39.0 — the write-class toolset completes

**Nothing to change.** Four additions; every existing operation behaves exactly as it did,
`run_shell` and `edit_file` included. A *Pins* row because the published shape grew (D9); protocol
3 unchanged, and no kernel change.

This is the rest of ENH-042 — the two halves you confirmed both cost you.

## `apply_patch(files[])` — a refactor is one act

```json
{
  "files": [
    {"path": "src/a.py", "edits": [{"old": "OLD", "new": "NEW"}]},
    {"path": "src/b.py", "edits": [{"old": "OLD", "new": "NEW"}]}
  ]
}
```

**Every edit in every file is checked before any file is written.** If one `old` is absent or
ambiguous anywhere in the batch, **nothing is written anywhere** and the refusal names the file. A
patch that wrote three files and then refused the fourth would leave a workspace no record
describes — the failure `edit_file` already refuses within one file, multiplied by the batch.

Also refused: an empty `files`, and **the same path named twice** — two entries for one file is a
caller who has lost track of their own batch, and applying both in order would work by accident and
hide the mistake.

It carries a `change` per file, the same block 0.38.0 put on a write:

```json
{"files": 2, "changed": [{"path": "src/a.py", "change": {...}}, {"path": "src/b.py", "change": {...}}]}
```

**Why `{path, edits}` and not a diff format** (D158): a patch format is a parser, and a parser is a
phase. `{old, new}` is the vocabulary `edit_file` already established, every refusal it has carries
over unchanged, and the validation is literally the same function. Codex's own patch is diff-shaped,
but what the kit owes you is a primitive, and its primitive for *change this region* already
existed.

## A background shell — three operations, not four

| | |
|---|---|
| `run_background(command)` | starts it, returns `{"job", "command", "pid"}` immediately |
| `job_output(job)` | `{"running", "exit_code", "output", "truncated"}` |
| `kill_job(job)` | stops it and **everything it started** |

You asked for "start, status, output, kill". Status and output arrive **together** (D160), the way
the field ships it: polling twice to learn one thing is a turn a model wasted.

Two things to build on rather than guess at:

- **`output` is what is new since you last asked**, not the whole buffer. Re-reading it on every
  poll would bill you for the same bytes over and over, which on a long build is the cost you would
  actually feel. `truncated` says the buffer overflowed and the earliest output is gone.
- **`exit_code` is `null` while it runs**, never `0`. Unknown, never zero — the rule `Usage` keeps
  for cache tokens (D141).

### Every job dies with the environment

**D157, and it is the decision that made this work.** D35 says a step owns the process tree it
starts and nothing survives the step — that is why `run_shell` ends its group in a `finally`. A
background job outlives its step by definition, so D35 cannot apply to it unchanged.

What carries over is the principle, one level up: **the environment owns a job, and closing the
environment ends every one of them.** That is the same move made for provider sessions after
BUG-019, where two children were found alive *ten hours* after their sessions ended, each holding a
subscription seat. A job nobody owns is that bug again.

So: **close your thread and your dev server is gone.** If you want one to outlive a thread, it is
not a job — start it yourself, outside the kit.

### And it is confined exactly as a foreground command is

A background job goes through the same sandbox wrap and is given the same narrow environment
(`KEPT_ENV` plus a `TMPDIR` inside the root) as `run_shell`. A job that escaped confinement *by
being long-lived* would be a hole opened by nothing but a lifetime — no mode admits it and no rule
names it.

Worth saying how we know: **removing the sandbox wrap from the background path broke no test.** The
claim that a job was confined was a docstring and nothing more until a mutation pass found it. There
are now two tests on it, and both fail when it is removed.

## How they are governed

From the one derivation, like every other operation:

| | derives as | so under `ask` |
|---|---|---|
| `apply_patch` | `write` | asks, exactly as `write_file` does |
| `run_background` | `run` | asks |
| `job_output` | `read` | **does not ask** — polling a build is a read |
| `kill_job` | `run` | asks |

`apply_patch`, `run_background` and `kill_job` are all **withheld in a `read-only` environment**
before governance is asked, because a mode is the environment's own promise and not one it
outsources.

`kill_job` asking under `ask` is deliberate and may annoy: killing a dev server is worth a
confirmation, and a product that disagrees grants an `allow` rule, which is the designed door
(D138's precedent).

## Not here

- **Scheduling, retries, or a job surviving a restart.** A job is a process this environment
  started, not a durable record.
- **Streaming a job's output as events.** The activity path exists for a foreground run; extending
  it to jobs is not what you asked for. Say if it would help.
