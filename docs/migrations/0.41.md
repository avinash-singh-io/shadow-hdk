# 0.41.0 — what a run carries into any provider

**One thing to know, and it is a fix you will want: a key-backed model was never receiving your
mode's instructions, and the thread was telling you it was.** That is BUG-229, below. Everything else
is additions — a *Pins* row because the published shape grew (D9); protocol 3 unchanged.

## BUG-229 — read this first

`ModelSession` stored `behaviour` and **nothing read it**. A key-backed model's system message was
built from the pattern's role plus a skill's prompt, so a mode's `system`, `append_system`, `model`,
`effort` and `temperature` all vanished.

And the reporting was worse than the drop. `Conversation` reads what a provider could not take off
the session by name — `getattr(session, "unmapped", ())` — and a `ModelSession` had no such
attribute, so **`thread.unmapped_behaviour` came back empty**, which reads as *your mode was honoured
in full*.

So when you wrote *"a key-backed model takes instructions and skills directly"*, it did not. Codex at
least named what it dropped; this dropped in silence and reported the opposite.

**What to check on your side:** any mode you run against a key-backed model has been running without
its `system`. If a Build agent behaved differently on a key than on a subscription CLI, this is why.

Fixed: instructions and fragments reach the system message, `Behaviour.model` reaches
`ModelRequest.model`, and `effort`/`temperature` are now **named** on `unmapped_behaviour` because
`ModelRequest` has nowhere to put them (D170).

## Named context fragments

```python
Behaviour(
    system="You are a careful reviewer.",
    fragments=(
        Fragment(name="house-style", text="tabs, never spaces", source="the plugin"),
        Fragment(name="AGENTS.md", text="...", source="the root myrepo"),
    ),
)
```

Each arrives framed, named and attributable:

```
<context name="house-style" source="the plugin">
tabs, never spaces
</context>
```

**One vocabulary for everything a run carries** (D166) — a mode's instructions, a root's `AGENTS.md`,
your house style, a team convention. Four mechanisms would have been four ways to be wrong, and a
model that has learnt to read one block has learnt to read all of them. Q1's bare `<instructions>`
is now one of these.

**One assembler, for a CLI and a key-backed model alike** (D167). That is what makes "identically for
both" — your words — a property rather than an intention. The two had already diverged: Q1 folded
into a CLI's turn while a key-backed model got nothing.

**A mode's `system` layers on the pattern's role for a key-backed model, never replacing it**
(D168). The pattern carries the loop's own mechanics — how to call a tool, when to stop — so
replacing it would remove the instructions that make the loop work. A CLI is the other case and
keeps `--system-prompt`'s replacing semantics, because there the CLI owns its loop.

### Fragments reach every provider, including one with its own flag

Worth stating because we got it wrong first: `instructions_in_prompt` gates *instructions*, not
fragments. No CLI has a flag for your named context, so the turn is the only way in — for Claude
Code, which has `--system-prompt`, exactly as much as for Codex, which has not.

We wrote it as one gate. Every unit test passed, because every one used a dialect that folds. **A
live measurement found it**: Claude Code answered by summarising its own system prompt with our
fragment nowhere in it. There is now a test for a CLI that has the flag.

## A root's own instruction files

```python
from shadow_hdk.adapters.agent.field_formats import root_instructions

# AGENTS.md, CLAUDE.md, or names you give
Behaviour(fragments=root_instructions(root))
```

ENH-047, as **a reader you compose** — not a default and not an agent tool (D169).

**The existing default stays:** a governed Claude Code does not read a folder's instruction files. A
run's instructions should be the mode's behaviour, not a file somebody left in a folder for a
different tool. What was missing was the other half — the kit never *offered* them either, so a team
convention written where the field writes it reached no provider, and a key-backed model never had
them at all.

Returning data rather than installing a default is the whole point: you decide whether a run gets
them, which is what makes them refusable.

An empty file is no fragment; a file too large is truncated and says so rather than dropped; an
unreadable one is skipped rather than fatal.

## `SKILL.md` and `AGENTS.md` as a skill source

```python
from shadow_hdk.adapters.agent.field_formats import markdown_skills

SkillRegistry((markdown_skills(where), store_skills(your_store)))
```

Your ask 11. The field's layout — `<dir>/<skill-name>/SKILL.md` — with front matter for `name`,
`description` and `needs`, and the body as the prompt. A file with no `name` takes its directory's,
which is how the field names them and what makes an existing folder work unchanged.

One malformed skill does **not** take the other twenty down: it is skipped, and `source.skipped` says
why, so you can show it rather than wonder.

Deliberately not a YAML parser. The front matter in practice is flat `key: value` lines, and pulling
a YAML dependency in to read three of them is the "a parser is a phase" trade we refused for the
patch format too. A file needing more than that is one you should read yourself.
