# 0.38.0 — a change is legible on the record

**Almost nothing to change.** The change on a write is an **addition**: every existing result key
keeps its place and its meaning, so anything you read today still reads. A *Pins* row because the
published shape grew (D9); protocol 3 unchanged, and no kernel change — the change rides the
observation's own output, not a new event field.

**One named behaviour change**, and it is the one you asked for: a `ServeHost` you hand a `sink=` to
**no longer keeps a run's proposals in the kit's own store**. See *What changed, not just grew*.

## Stop reading the disk to find out what changed

`write_file`, `edit_file` and `delete_file` now carry a `change` on their result:

```json
{
  "path": "src/app.py",
  "bytes": 1284,
  "change": {
    "diff": "--- a/src/app.py\n+++ b/src/app.py\n@@ -14,3 +14,3 @@\n-    return None\n+    return result\n",
    "truncated": false,
    "added": 1,
    "removed": 1,
    "created": false,
    "deleted": false,
    "before_unreadable": false
  }
}
```

That replaces reading the environment's root yourself. Reading the disk raced the agent, and — the
reason this is a primitive rather than a convenience — **it could not work at all** for a contained
or remote environment, where the host has no such access.

### What each field means

| | |
|---|---|
| `diff` | unified, standard, `a/`–`b/` prefixed. `""` when nothing changed — an agent rewriting a file with what was already in it is a real and common act, and the record says the file did not move |
| `truncated` | the diff was cut at the cap. **4096 bytes**, one named constant (`CHANGE_DIFF_BYTES`) |
| `added` / `removed` | **exact line counts, computed over the whole diff before it was cut** — so a truncated diff still tells you the true size of what happened. `null` only when the prior state could not be read |
| `created` | there was no file before |
| `deleted` | there is no file after |
| `before_unreadable` | the prior state is not text this surface can carry — a binary file, or a read that was denied |

### Why a diff and not before-and-after content

You settled this: content to a cap, `truncated` past it, no per-file version history because git
keeps that for a repository. A diff is what survives the cap usefully — before-and-after cut at 4 KB
of a 1 MB file shows nothing of a three-line change, while a diff of the same change shows all of it.

### `move_file` carries no change, deliberately

A move is the one write-class act with no content delta. `from` and `to` are the whole story, and a
zero diff beside them would read as *nothing happened*. Render a move from its inputs.

### Two honest edges

- **An unreadable prior state never fails the write.** A write that failed because the
  record-keeping failed would be the tail wagging the dog: the act your mode admitted and your user
  approved still happens, and `before_unreadable` says what could not be captured.
- **`added`/`removed` are `null`, not `0`, when nobody could measure them.** The same rule `Usage`
  keeps for cache tokens (D141): unknown, never zero.

## What changed, not just grew

### The kit keeps your run's creations only when nobody else is listening

You asked for this: a run's creations should arrive as a proposal and be stored by you once agreed,
not kept inside the kit. `KeepingSink`'s own rule is *whoever holds the sink decides*, and the
shipped composition was deciding on your behalf.

The rule now states itself:

| you pass | the kit's store |
|---|---|
| `sink=your_sink` | **nothing kept** — you hear every proposal and store what you agree to |
| no sink | kept, as before (ENH-011: with nobody listening, a store row is the only way a minted skill survives a restart) |
| `keep_proposals=True` | kept, whatever else you passed |
| `keep_proposals=False` | never kept |

**If you already pass a `sink=`, this is the change to know about**: proposals stop appearing as
`skills` rows in the kit's store. That is what you asked for, and `keep_proposals=True` restores the
old behaviour if anything of yours was relying on it.

Nothing narrows to skills any more, either: a `memory` or an `instruction` an agent proposes reaches
your sink the same way a minted skill does.
