# Migrating from 0.30.0 to 0.31

Phase 36 (Epic 0009, *the harness as data*) adds **plan admission**: a plan an agent, a CLI or a
host proposes is a `Composition` — no new grammar (D107) — judged whole before its first step
runs, under limits that narrow host → mode → parent (D109). Nothing an existing caller does
changes: a call that proposes no plan is a plan of one step and is admitted as it always ran.
The wire protocol stays at `3`; every addition below is a new method or a new field.

## What a host reads

- `plan_admitted` and `plan_refused` join the event stream and the fold (`Item.plan`). An admitted
  plan names `asks` and `refusals` — the steps the policy *will* ask about or refuse when they run
  — so a host can present a plan's questions as one card; each step is still asked or refused live
  at its own invocation (D108, D121 as amended). A refused plan names every `mismatch` (axis,
  step, required, found) in stable order: depth, fan-out, steps, then components by leaf.
- `plan_refused` is an error kind on the wire, alongside `capability_mismatch`.
- `thread/start` and `thread/resume` accept `plan_limits: {depth, fan_out, steps}` — the host's
  own ceiling, met with the mode's at every turn — and return `plan_limits`, what the next plan is
  admitted under; `thread/set_mode` returns the new value. `modes/list` carries each mode's `plan`.
- `thread/amend {thread_id, handle, composition, answer?}` continues a parked plan on a different
  composition (D116): admitted like the original, or refused with the plan untouched and the
  question still open. Returns `{admitted, mismatches, events}`.
- `thread/start`, `thread/resume` and `thread/set_mode` return `unmapped_behaviour`: the behaviour
  fields the mode set that the provider has no flag for (ENH-020). A host hides those controls
  instead of showing one that does nothing; before 0.31 the field was silently dropped.

## In process

```python
from shadow_hdk.kernel import PlanLimits

thread = await Thread.open(..., plan_limits=PlanLimits(depth=3, fan_out=8, steps=64))
thread.plan_limits  # the host's met with the mode's, live
thread.unmapped_behaviour  # ("system", "model") on a mode Codex cannot honour
await thread.amend(handle, composition, Allow())
```

`kernel.admit(composition, registrations, limits)` is pure and importable on its own; `Children`
calls it in `spawn` for every plan, whoever proposed it. `runtime.planning.plan_components()` is
the `compose` component — offered beside `ask_person` by `serve`, so a resident CLI plans through
the socket the way the model loop's meta-tool does (D110). A `Pattern(absorb=False)` runs an
admitted plan after its planner's step closes rather than inside it (D112).

## Modes

A mode document may carry a `[plan]` table; an axis left out is the named policy's shipped value
(read-only and ask: 3 / 8 / 64; workspace-write: 4 / 16 / 128; full: 4 / 32 / 256), and a table
wider than its policy is refused by name. A host that wants more composes a `ModeSpec` in code.

## Fixed

- A step that parked a second time in one leg — a plan that asks twice, or a refused amendment
  followed by an admitted one — was handed its first answer again (LangGraph replays a task's
  resume values by index). The executor drains the replays and hands the component the newest;
  `Thread.settle` keeps a question the run parks on again (BUG-055).
- The README's Python and TypeScript snippets are run by the suite again (BUG-054).
