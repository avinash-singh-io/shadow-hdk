# 0.43.0 — an agent is data, like everything else

**Nothing to change.** Additions only: a store source, a field on a mode, a parameter on
`thread/start`, a listing, and a field on the thread's reply. Every existing composition behaves
exactly as it did — a mode naming no agent still gets `single`, and a test pins that. A *Pins* row
because the published shape grew (D9); protocol 3 unchanged.

## The gap this closes

Skills, modes, rules, batteries, providers and component switches all lived in your database and
were read back by the kit. **Agents did not.** An agent architecture could only come from a packaged
TOML or a file path, there was no listing for one, and `ServeHost` hardcoded `single` — so every
thread a host ever opened ran the same loop.

A plugin whose Build agent, Reviewer, Test fixer and Release writer cannot be stored or selected is
not a plugin; it is one hardcoded role. That was the last asymmetry.

## An agent is a store row

```json
{ "name": "reviewer", "system": "You review a change and say what is wrong with it." }
```

Put it in the `agents` collection — `store/put`, like any other row. Optional beside those two:
`meta_tools`, `tool_names`, `ceiling`, `max_turns`, `nudge`, `catalogue_threshold`.

Read with `store_patterns(store)`, version-gated like `store_skills`, so the next read sees your
write. **A malformed row is skipped, not fatal** — one bad agent must not take the other three
down — and `skipped` says why, so nobody debugs an agent that silently never appeared.

Your row **shadows a shipped one of the same name**, as a skill does: later is closer to the run.

## A mode names which agent runs it

```json
{ "id": "reviewing", "policy": "workspace-write", "agent": "reviewer" }
```

On the mode because a mode already says *who the model should be* (`behaviour`) and *what it may
do* (policy, plan limits); which loop runs it is the same kind of fact. It also means switching
agent goes through **`set_mode`** — a door that exists and is governed — rather than a new one.

`thread/start {"agent": "builder"}` overrides it for one thread.

### An unknown name is refused, naming what there is

```
no agent called 'reviewr' is registered here; there is: builder, critic-pair, reviewer, single, …
```

Never a silent fallback to `single`. A run that looks right and is not is the worse failure, and
this is the cut `Dialect` makes for an unknown transport and `ModeRegistry` for an unknown mode id.
The refusal happens **before** an environment is opened or a model is asked, so it costs nothing.

## `agents/list`, and what a run resolved to

`agents/list` returns `{"name", "description"}` per agent — the shipped library and yours, sorted —
completing a symmetry `modes/list`, `rules/list`, `skills/list`, `tools/list`, `batteries/list` and
`providers/list` already had.

`thread/start` now answers with **`agent`**: the name it actually resolved to. That is for the
resolved snapshot you cache by hash — you cannot build one if the kit will not say which agent ran.

- a named agent → that name
- nothing named → `"single"`, not empty, because empty reads as *we do not know*
- a CLI provider → `""`, because it owns its own loop and naming one would be a claim we cannot make

## Not here

- **Any notion of a plugin.** An `agents` row is a `Pattern`, not a plugin; bundling is yours.
- **Agent inheritance or composition.** A Reviewer built from a Base means writing both rows.
- **Changing what a `Pattern` is.** Same fields, now from a different place.

## And one thing that was always there

While writing this we found that `store/put`, `store/get`, `store/delete`, `store/list` and
`store/version` are on the wire with no collection allow-list — so full CRUD on *every* concept in
this document has worked for a long time and was documented nowhere. That is now the opening
chapter of [`docs/for-a-product.md`](for-a-product.md), which this release also brings current
after eight releases of drift.
