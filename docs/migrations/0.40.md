# 0.40.0 — undo, and an agent's own workspace

**Nothing to change.** A new port with a shipped adapter, three operations, and a host-side helper —
all additions. A *Pins* row because the published shape grew and a **port** was added (D9,
project-rules); protocol 3 unchanged.

ENH-043 and your ask 7.

## Undo

You narrowed the design question for us — *a port with a git-backed adapter, where a root is a work
tree, covers our first use case* — and that is what shipped.

### The port

```python
class WorkspaceHistoryPort(Protocol):
    async def snapshot(self, label: str = "") -> str: ...
    async def restore(self, snapshot: str) -> None: ...
    async def snapshots(self) -> Sequence[Snapshot]: ...
```

A port because *cheap on a work tree, expensive otherwise* is exactly what a port is for: on a
repository you get `GitHistory` for free, and on a remote or contained root you write your own. An
environment without one **refuses and does not crash**, like every port default here.

`environment.history` is it, and on a local root it is attached automatically wherever `.git`
exists — including a **linked worktree**, where `.git` is a file rather than a directory.

### You decide when to snapshot (D162)

Nothing snapshots automatically. You described "a snapshot before a turn's first write", and that is
a *policy* — the kit cannot know whether a turn deserves one, and the boundary rule puts policy your
side of the port. So:

- **Your per-turn checkpoint** goes through `environment.history.snapshot(...)` directly. That is
  your act, not the agent's: nothing is judged and nobody is asked, which is what makes an automatic
  per-turn checkpoint viable at all.
- **The agent's own checkpoint** is the `checkpoint` operation, and the mode judges it like any act.

### Three operations for the agent

| | derives as | under `ask` |
|---|---|---|
| `checkpoint(label?)` | `write` | asks |
| `restore(snapshot)` | `delete` — **irreversible** | **asks** |
| `list_checkpoints()` | `list` | does not ask |

**`restore` is irreversible and `ask` stops a person before it (D163), deliberately.** It overwrites
work that may be on no snapshot, so `reversible=True` would be a claim the mechanism cannot keep —
and an undo is precisely the act somebody should be asked about. This is one of the few places where
the conservative derivation is also the better product. *An undo that bypasses governance is a
hole*, which is what we told you, and this is that kept.

`checkpoint` derives as `write` rather than as a read, even though it changes no file you can see:
it writes objects into the repository, and deriving it as a read to spare a person the question is
the convenient under-claim `ASSUME_WORST` exists to refuse.

### What a snapshot holds — read this one (D164)

**A snapshot holds what git would track.** `.gitignore` decides, so `node_modules` and `.venv` are
not captured — which is what makes a snapshot cheap enough that anybody takes one.

The consequence runs both ways, and both are tested:

- **A restore does not delete an ignored file.** Your `node_modules` survives an undo. An undo that
  deleted it would be an undo nobody dares use.
- **A restore does not resurrect one either.** If `.env` changed since the snapshot, it is left as
  it is. Bringing back somebody's rotated secret is its own kind of bug.

### We never touch your git state (D165)

Not HEAD, not a branch, not the index, not the stash, not anything `git log` shows. A snapshot is
built through a *temporary* index into a parentless commit object under
`refs/shadow-hdk/snapshots/<id>`:

```
GIT_INDEX_FILE=<scratch> git add -A  →  write-tree  →  commit-tree  →  update-ref
```

So `git status`, `git stash list`, `git branch` and your staged changes are exactly as you left
them — asserted before and after both a snapshot and a restore. A kit that left entries in your
stash is a kit you would stop trusting with your repository, and rightly.

Cleaning up a month of snapshots is one `git for-each-ref refs/shadow-hdk/snapshots` away.

**Snapshot ids sort.** A commit's date is second-resolution, so two snapshots taken in the same
second tie and "newest first" becomes whatever git felt like — which is exactly what checkpointing
every turn produces. The id carries the order instead.

## An agent's own workspace

```python
from shadow_hdk.adapters.environment.worktrees import open_worktree, close_worktree, worktrees

# its own directory, on its own branch
tree = await open_worktree(repo, "agent-one")

# ... run an agent on tree.path ...

# the directory goes; the branch stays
await close_worktree(tree)
```

Each agent gets a real checkout on `shadow-hdk/<name>`, sharing the object store rather than copying
the tree — cheap enough to do per agent, and separable afterwards because **each has a branch you can
open a pull request from**. `close_worktree` keeps the branch by default: the work on it is the
point, and it outlives the directory it was written in. Pass `keep_branch=False` for a run you threw
away.

**Host-side, not an agent tool.** Deciding that a run gets its own workspace is a composition
decision. An agent registration for it would let a model invent branches nobody asked for, and no
mode has anything sensible to say about that.

**Your own branches and worktrees are unreachable from here.** Every branch is created under
`shadow-hdk/`, and `worktrees()` lists only those — so a cleanup cannot sweep up a worktree you made
yourself. That is asserted with a developer's own worktree sitting right beside the kit's.

## Not here

- **A remote or contained history adapter.** The port exists so you can write one; say if you would
  rather we did.
- **Restoring across repositories**, and snapshotting ignored files (D164).
- **A cloud sandbox for isolation.** Worktrees are the local answer; where a cloud sandbox lives is
  still your §5 "to agree".
