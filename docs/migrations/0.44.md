# 0.44.0 — the claims are true

**One thing to check before you pin this, and five things to stop working around.**

> **Check your mode documents for `tools_offered` first.** It used to parse and do nothing, so a
> name that matched no component was harmless. It is now **refused at the start of the turn**, naming
> the name and listing what the run does offer. That is the point of the change — a typo that
> silently narrowed nothing is what made the field untrustworthy — but it means a mode document with
> a stale or misspelled name turns from quietly wide into a refused turn. If you have any
> `tools_offered` set, check each name against the components you register. A mode that sets none is
> unaffected, which is most of them.

Beyond that: This release fixes claims the kit
already made and did not keep. If you read `unmapped_behaviour` or `thread.agent` and planned against
what they said, some of what you planned around was our defect, not your constraint.

A *Pins* row because the published shape grew (D9); protocol 3 unchanged. Every existing composition
behaves as it did, and each item below has a test pinning that.

## Five claims, now true

### A mode's `tools_offered` narrows what a step is shown

It parsed, it was reported as honoured, and **nothing narrowed anything** (BUG-230). A run told to
offer one tool was offered all of them.

```json
{ "id": "reading", "policy": "read-only", "behaviour": { "tools_offered": ["read_file"] } }
```

Now that is what the model sees — in both catalogues, which is the part worth knowing: a key-backed
model is *handed* a list, while Claude Code and Codex **ask** the registry over MCP. Narrowing only
the first would have left the claim false for the providers you actually run. A narrowed name is also
not callable, so a CLI holding a listing from before a `set_mode` cannot reach past it.

Both doors move together: the list a CLI is **served** narrows and so do its **calls**. The first cut
of this release narrowed only the calls (BUG-235), which served a model the whole catalogue and then
told it *no component named …* for anything it picked — worse than either half alone, and the same
class as every *no tools* defect this kit has had. It is fixed and both doors have a test.

Narrowing is applied **last**, so it can only take away — no mode widens past its policy by naming
something. A name no component answers to is **refused, naming it and listing what there is**: a
typo that silently narrowed nothing was the failure worth refusing.

If you were enforcing a tool limit yourself because ours did nothing, you can stop.

### A mode's `model` reaches a key-backed model

`ModelRequest.model` carried it and `LangChainModel` discarded it (BUG-231), while the honesty field
named `effort` and `temperature` and not `model` — so one host could not run a cheap model for one
mode and a strong one for another, and nothing said so.

Now the adapter builds a chat model for the asked-for spec and keeps one per spec, with the keyword
arguments you constructed it with, so a second spec on an OpenAI-compatible endpoint still gets its
`base_url` and key.

**`LangChainModel.over(chat)` cannot do this** — a chat model you configured yourself cannot be
re-specified — so it reports `selects_model` false and `thread.unmapped_behaviour` names `model`.
That is the honest answer, and it is new information: it was being dropped in silence before.

### A key-backed thread's later turns contain its earlier ones

Every turn opened with the role and the new prompt, so turn three could not see turns one and two
(BUG-232). Ask *what did I just ask you* and the model could not know. A CLI-backed thread never had
the problem, so behaviour differed by provider with nothing saying which.

The transcript is now the thread's. The role is still rebuilt each turn, so a `set_mode` is never
shadowed by a stale one, and it survives the provider reopen a `set_mode` performs.

**It is unbounded** (ENH-052). This is what every chat API does, and fitting a transcript to a
model's window is a budget and a compaction — neither of which this kit has yet. A long thread will
reach the window. If that matters to you now, cap your own turns or enable the `compact` meta-tool on
your pattern.

### A turn is given up for silence, not for taking long

One fixed `asyncio.timeout(600)` wrapped the whole wait, so a turn was failed for *being long* —
with the diagnosis *the provider did not finish within 600s* (BUG-233). And the clock counted time
waiting for a human being, so a person who took twenty minutes to approve failed the turn and the
provider was blamed.

The ceiling now measures the **gap between frames**. A CLI that keeps streaming is never given up on,
however long the run takes; one that stops is given up on after the ceiling, and says *the provider
said nothing for Ns*.

The default is **1800 seconds of silence**, not 600 of work — a different number because it measures
a different thing. A mode may set its own:

```json
{ "id": "patient", "policy": "workspace-write", "behaviour": { "silence_seconds": 3600 } }
```

And time the kit spends answering the provider's own call — your policy's judgement, your component,
a person's approval — is given back to it.

### A selected agent survives a mode switch and a resume

0.43.0 made an agent selectable per mode and readable on the thread, and carried it through neither
door you actually use (BUG-234): `set_mode` never re-resolved it, and `ThreadRecord` had nowhere to
keep it, so a resumed Reviewer thread came back as `single` — and reported `single`, truthfully,
about a run that was supposed to be a Reviewer.

Now `set_mode` re-resolves (and refuses an unknown name on the new mode, naming it), and a resume
restores what the record says. A `thread/start {agent}` override goes on winning across both.

**The record gained two fields**: `agent` and `agent_override`. If you map `ThreadRecord` to columns,
read `version` first as you already do; a record written before this reads them as empty, which means
*no agent in particular*.

## What is still not measured

Codex's instruction fold has never run end to end — the laptop this was written on has a Codex that
refuses every model it is offered. The two live tests skip, and the skip now **says what account it
needs and what it would prove** (TD-020). Nothing claims otherwise.
